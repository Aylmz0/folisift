styles. A style change must not require rewriting `guide.md`.

## 2. Shared invariants

1. **MCP is hands, host LLM is brain.** The server parses, caches, validates,
   renders, audits and reports. The host LLM reads sources, decides what
   matters, writes prose and fixes content.
2. **No LLM call, shell, network or arbitrary Typst inside the server.**
3. **Content is style-neutral.** One semantic `guide.md`; styles change
   presentation, structures and localized labels, not facts.
4. **Coverage is style-neutral.** Every source section is claimed exactly once,
   via `## <number>` or `covers` metadata.
5. **Source refs are mandatory.** No invented pages, formulas, dates, quotes or
   citations.
6. **Audit section is mandatory.** Every structure ends with a localized
   coverage/limitations section.
7. **Deterministic layout.** LLMs do not generate HTML/CSS/Typst. Templates and
   tokens own typography, pagination, tables, figures and TOC.
8. **One content hash across styles.** Normalized prose hash must match except
   for localized labels and TOC/audit headings.
9. **Source cache is content-addressed.** Hash + parser version + OCR mode.
10. **Builds are idempotent.** Same content + style + engine → same PDF and
    same content hash.
11. **No silent truncation.** Every limited tool result says what was omitted
    and how to continue.
12. **Accessibility is a gate.** Contrast, font size, tagged PDF, reading order
    and bookmarks apply to every stable style.

| Work | MCP server | Host LLM |

| Source search | yes | no |

The server must never ask the LLM to do a deterministic step: counting pages,
extracting text, parsing tables, checking headings, rendering PDFs, measuring
overflow, or formatting styles.

## 4. Tool budget

v0.2 has 10 tools. The roadmap adds **two** intent-level tools, for a cap of 12:

| Tool | Version | Purpose |
|---|---|---|
| `prepare_guide` | v0.3 | analyze all sources + create skeleton + return a read/write plan in one call |
| `style` | v0.4 | `list` / `info` / `preview` styles |

`prepare_guide` is the default entry point. Granular `analyze_source`,
`scaffold_guide` and `read_source` remain for debugging and recovery.

`prepare_guide` returns:

```json
{
  "guide": "guides/pd0-pd1",
  "content": "guides/pd0-pd1/guide.md",
  "style": "paper",
  "sources": [
    {"source": "sources/PD0.pdf", "pages": 123, "text": "data/cache/..."}
  ],
  "outline": [
    {"heading": "0.1 Giriş ve amaçlar", "covers": ["PD0:0.1"], "read_pages": "1-20"}
  ],
  "next": [
    "read_source source=sources/PD0.pdf pages=1-20",
    "write guide.md",
    "build_guide check=true"
  ]
}
```

It must not write prose. It writes the skeleton, cache and a plan.

`style` actions:

- `list`: ids, status, languages, structures, domains.
- `info`: tokens summary, compatibility, preview path.
- `preview`: render a small canonical sample, not the full guide.

## 5. No repeated-LLM-work rules

The host agent repeats itself when the server returns raw data, hides state, or
forces a full rebuild for every tweak. The server must make the following
cheap and explicit:

1. **Analyze once.** `prepare_guide` uses the source cache; a second call with
   the same source is a cache hit.
2. **Read chunks once.** `read_source` returns `next_pages`; the agent does not
   re-read the same pages to discover the next range.
3. **Search before reading.** `search_source` returns page snippets so the
   agent does not dump whole sources.
4. **Write sections, not the whole book.** The agent writes `guide.md` with its
   native `write`/`edit`; MCP does not stream the whole file.
5. **Build once per content revision.** `build_guide` returns a content hash;
   unchanged content returns the cached output.
6. **Fail narrowly.** Coverage/layout responses name only failing sections,
   pages and rules; they do not dump the full document.
7. **Preview cheap.** `style` preview renders one sample; style choice does not
   rebuild the full guide.
8. **Diagnose before asking.** `doctor` checks sidecar, PDFium, fonts, cache,
   config and MCP handshake without LLM involvement.
9. **No style rewrite.** Choosing a style after content exists must not require
   rewriting prose; only structure/label changes.
10. **No tool loop for a single outcome.** `prepare_guide` replaces the
    analyze → scaffold → plan sequence.

## 6. Caching and idempotency

| Cache | Key | Invalidation |
|---|---|---|
| Source text | source SHA-256 + liteparse + OCR + cache version | source/parser change |
| Inventory | same key | same |
| Page images | source hash + pages + DPI + renderer | source/renderer change |
| Build | content hash + style + engine version | content/style/engine change |
| Style preview | style id + version + sample hash | style/engine change |
| Tool responses | optional, bounded | argument hash; never hide errors |

Rules:

- Atomic writes; no partial cache.
- Cache lives under `data/cache/`, gitignored.
- `build_guide` returns `content_hash`, `cache_hit`, `page_count`.
- `prepare_guide` returns `cache_hit` per source.
- Repeated identical calls are safe; no duplicate files.
- Do not cache errors forever; retry on a changed key or explicit `force`.

## 7. Layout quality gates

These are deterministic checks, not “LLM looks at it”:

| Check | Rule |
|---|---|
| Empty page | no intentional full-page figure and < 5% content area → fail |
| Text overflow | text outside content box → fail |
| Orphan heading | heading in bottom 12 mm without following body → fail |
| Widow line | single last line before page break → warn/fail by threshold |
| Table split | small table split; header not repeated on continued table → fail |
| Figure split | figure or caption split from its body → fail |
| Box split | definition/critical/example/note split across pages → fail |
| TOC | entry page numbers resolve; no missing/duplicate entries |
| Bookmarks | heading tree matches TOC depth |
| Turkish glyphs | no missing glyph / replacement character |
| Code overflow | raw block wider than content or clipped → fail |
| Page count | paper: 22 ±0; other styles: declared target ±10% |

Implementation can use:

- Typst compilation + PDFium page boxes;
- `liteparse` text bounding boxes / page screenshots;
- generated PDF text extraction;
- page image analysis for blank/overflow;
- stable page snapshots for regression.

Do not use an LLM for these checks.

## 9. Research signals

- LLMs generating raw styled HTML/PDF produce inconsistent layouts; a
  deterministic presentation layer is more reliable:
  <https://blackstork.io/blog/document-generation-for-ai-agents>
- Design-system compliance improves when rules are executable artifacts
  (tokens/registry), not prose instructions:
  <https://dl.acm.org/doi/full/10.1145/3772363.3798616>
- Agents retry and repeat tool calls; idempotency and caching are required:
  <https://www.firecrawl.dev/blog/agent-tools>
- MCP tools should be intent-level, not endpoint mirrors; five calls for one
  outcome is the wrong abstraction:
  <https://www.itential.com/resource/blog/designing-mcp-servers-for-infrastructure>
- Context bloat and response size are recurring MCP failures; bound outputs and
  return paths/summaries:
  <https://aws.amazon.com/blogs/machine-learning/mcp-tool-design-practical-approaches-and-tradeoffs>
- PDF MCP users want page ranges, OCR flags, citations and bounded responses:
  <https://pdfvision.dev/guide/mcp-server>
- Study-guide quality is not just prose: worked examples, concrete examples,
  dual coding and elaboration matter:
  <https://pmc.ncbi.nlm.nih.gov/articles/PMC5780548/>

## 11. Open decisions

1. Is the tool cap 12 acceptable, or should `style` live only in CLI/resources?
2. Should `prepare_guide` write the skeleton or return a patch for the host?
3. Is `paper` page count exact 22, or 22 ±1 if typography improves?
   v0.3 currently assumes exact 22.
4. Do `covers` markers use HTML comments or a `::: section` directive?
5. Which layout audit checks are hard fails vs warnings?
6. Is `en` the only new language in v0.4, or `tr` + `en` + one RTL spike?
7. Do style previews render PDF, PNG or both?
8. Do we expose style tokens as a resource or only a summary?

## 12. Definition of harmony

- Every plan names the same version boundary and default style.
- No tool appears in two versions with different semantics.
- No style or layout change alters content or coverage.
- Every deterministic operation has one owner: MCP.
- Every creative decision has one owner: host LLM.
- Every release has one visual/content gate and one clean-install gate.
- The host agent can complete a guide with one preparation call, bounded reads,
  one write pass and one build per revision.
